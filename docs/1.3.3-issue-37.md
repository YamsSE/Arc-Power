# 1.3.3 — issue #37 follow-up

## Reported after 1.3.2

1. Applying only a negative voltage offset (`-75 mV`, core clock `0`) makes
   the core-clock value jump to a positive value such as `+172 MHz`. It appears
   in the saved profile summary and then in the Tuning card.
2. Manual fan applies start failing after several changes in one session.

## Undervolt `+172 MHz`

### Cause

The Alchemist negative-voltage path uses the legacy Sysman interpolative
sequence: `OcSetMode(INTERPOLATIVE)` → `OcSetFrequencyTarget(live clock)` →
`OcSetVoltageTarget(target, offset)`. Extending the V/F curve this way makes
the driver report a derived positive IGCL frequency offset even though the
request contained no frequency offset.

The native apply correctly returns the post-apply driver state. The Tuning page
then re-syncs every control that was not part of the apply payload, so the
derived value replaced the user's `0 MHz`; a later “Save as Profile” captured
it, and the next apply carried it as if the user had requested it.

### Fix

- `backend/services.rs` captures the IGCL frequency offset from the pre-apply
  snapshot. After a successful negative-voltage Sysman apply, the returned
  `state.gpuFreqOffsetMhz` is set to the requested offset when the payload
  contains one, otherwise to the pre-apply value. The derived driver value is
  never reported as a core-clock setting.
- `pages/tuning.ts` applies the same rule on the renderer side (covering the
  compatibility/broker route): if the apply payload did not request a frequency
  offset, the fresh state keeps the prior value.

Profiles created while the old behaviour was active may still store the
derived value; re-saving the profile after applying `0 MHz` stores the correct
value.

## Manual fan apply after several changes

### Cause

When the driver refuses the dedicated fixed-speed setter, the apply falls back
to a flat speed table. The verification required the driver to report
`curve` mode. A card that accepted the flat table while keeping its previous
`fixed` mode therefore failed the read-back, and every later manual apply
followed the same path and failed.

### Fix

- `backend/fan_apply.rs` accepts the flat-table fallback when the driver reports
  `fixed` mode and the fixed speed matches the requested percentage. A genuine
  mismatch or a genuine setter/read-back failure still fails.
- The read-back settle window is extended from six 100 ms reads to twelve
  150 ms reads (~1.8 s) without repeating a setter. A slow fan controller no
  longer turns a valid write into a false failure after rapid applies.

## 1.3.4 addendum — read-side guard

The 1.3.3 fix corrected the apply response and the renderer's re-sync, but a
later `get-current-settings` read (Stock/Advanced toggle or a fresh session)
could still return the driver's derived positive frequency offset. 1.3.4 adds a
per-device session guard in `backend/services.rs`:

- A negative-voltage apply records the requested frequency offset, or the
  effective value already in the returned state.
- Every later `get-current-settings` read for that device reports the guarded
  value instead of the derived getter value.
- An explicit frequency-offset apply replaces the guard.
- A zero/positive voltage apply or reset-to-defaults clears it, so the
  driver's real value is shown again.

The guard is session-scoped. A derived value that already persisted across a
restart is still shown on the first read; applying `0 MHz` once clears it and
is then kept for the session.
