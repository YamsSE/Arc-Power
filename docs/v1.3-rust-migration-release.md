# Arc Power 1.3.0 Rust migration release

> Packaging status update (2026-11-17): the native distribution now builds
> NSIS self-extracting setup and portable wrappers without Electron Builder.
> The `Arc-Power_Tauri.zip` archive contains both wrappers. The native wrapper
> flow carries the complete compatibility payload and forwards the 1.2.5
> updater arguments; desktop acceptance remains unverified.

This release must remain installable by the **1.2.5 updater**, which is already
in users' hands and cannot be changed. The 1.2.5 updater is strict; any mismatch
below makes the in-app upgrade silently unavailable or fail verification.

## Release identity

- Tag: **`v1.3.0`** exactly. The 1.2.5 parser accepts only `v?<major>.<minor>.<patch>`;
  `v1.3` or `1.3` is ignored.
- Publish as the repository's **latest** release (not draft, not prerelease).
- Assets, exact names:
  - `Arc-Power_Installer.exe` — installed-build update
  - `Arc-Power_Portable.exe` — portable-build update
- Every uploaded asset must expose a GitHub `digest` of
  `sha256:<64 lowercase hex>`. The 1.2.5 updater refuses an asset without a
  valid digest. Never upload a bare Tauri default name such as
  `Arc Power_1.3.0_x64-setup.exe`.

## Build contract

Build the Tauri host and the complete compatibility payload, then stage both
native wrappers:

```powershell
node scripts/build-tauri-dist.mjs <release-host.exe> <compatibility-win-unpacked> <new-output-directory>
```

The staged payload must contain:

- `Arc Power.exe` — the native Tauri host
- `resources/` — the root icons
- `compatibility-backend/ArcPower.Backend.exe`
- `compatibility-backend/resources/app.asar`

`Arc-Power_Installer.exe` and `Arc-Power_Portable.exe` are native NSIS
self-extracting wrappers, not Electron Builder artifacts. The installer
wrapper passes `--install` for a user setup launch and forwards the strict
`--update --update-parent-pid <pid> --update-install-dir <dir>` handoff to the
native Tauri host. The portable wrapper passes its path as the portable build
marker and runs the native host with the staged compatibility service beside it.

## 1.2.5 installed update flow

1. 1.2.5 checks `https://api.github.com/repos/YamsSE/Arc-Power/releases/latest`.
2. It sees `1.3.0 > 1.2.5`, selects `Arc-Power_Installer.exe`, verifies the
   SHA-256 digest, and runs it with the `--update` handoff above.
3. The NSIS wrapper extracts the full package to a temporary directory and
   forwards the update arguments to the native Tauri host.
4. The native update worker verifies and replaces the full installed payload,
   updates `DisplayVersion`, preserves `%APPDATA%\ArcPower`, relaunches the
   installed `Arc Power.exe` without portable wrapper variables, and exits.

## 1.2.5 portable update flow

1. 1.2.5 selects `Arc-Power_Portable.exe` and verifies the digest.
2. Its PowerShell handoff waits for the old process to exit, replaces the
   wrapper on the same volume, relaunches it, and requires it to stay alive for
   8 seconds.
3. The 1.3 wrapper extracts the full Tauri payload and starts the native host.
   `%APPDATA%\ArcPower` is preserved.

## 1.3.0-side updater (current behaviour)

In a normal non-mock Tauri run the 1.3.0 host owns its own update flow
natively: the splash update decision and its timeout (`startup_update.rs`),
the GitHub `releases/latest` fetch and pure release selection
(`update_hub.rs` over `backend/update_release.rs`), the verified streaming
download with an opaque one-use receipt token, and the install handoff
(`--update` for installed builds, `--portable-update` for portable builds).
Electron's `auto-update.js` path remains the standalone and mock fallback,
and a standalone check may reuse the same pure selector through
`update-release-select`. These native paths are not live-verified yet: the
recorded local validation covers the portable smoke test only, and the
installed `--update` handoff against a real 1.2.5 installation plus a full
GitHub round trip remain the acceptance gate.

## Verification checklist

- Clean **1.2.5 installed** build → in-app update → 1.3.0 starts. Profiles,
  settings, recording metadata and OBS credentials survive.
- Clean **1.2.5 portable** build → in-app update → wrapper is replaced and
  1.3.0 starts. The same user data survives.
- `app-version` and `app:build-info` report `1.3.0` and the correct
  portable/installed kind.
- Release tag is `v1.3.0`; both asset names and their digests match exactly.
- No update loop: after upgrading, the 1.3.0 updater sees the same version and
  reports no update.

- Built the 1.3.0 Electron compatibility `win-unpacked`.
- Staged `Arc-Power_Portable.exe` and `Arc-Power_Installer.exe` (137.1 MB each,

- Payload verified: `Arc Power.exe` 1.3.0 plus

  final acceptance gate.

## Do not

- Rename the release assets or split the installer/portable into different
  names.
- Tag `v1.3` instead of `v1.3.0`.
- Publish a draft/prerelease as the update target.
- Remove `compatibility-backend` from the 1.3 payload; unmigrated
  compatibility channels (GPU apply roots, tray actions and other brokered
  services) still depend on it.
