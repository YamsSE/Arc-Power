# Version 1.2.4: Graphics and runtime corrections

## Repeated helper launches

Arc Sleep reads the selected GPU's FPS limiter even with both policies disabled. In 1.2.3 those reads also queried legacy driver sharpening, launching a disposable `Arc Power.exe` helper for every read. Arc Sleep now opts out of that unrelated sharpening query, and unified GPU routing forwards the option while retaining the selected adapter's identity. Ordinary explicit Graphics reads retain their existing behavior. FPS values are still read fresh.

The RTSS profile helper now obtains runtime information independently of the startup-registration settings view. Running-process discovery stays current; installed/custom-path fallback is cached for 30 seconds. Explicit startup settings reads and registration-write verification still query the registry. The helper also receives a real executable working directory.

Unexpected helper exits and timeouts retain a bounded stderr tail in the returned error and the application's `[rtss]` log. Clean shutdown stays quiet. A failed helper is not automatically restarted, because it may own temporary profile changes whose state must be preserved.

RTSS installation detection, running-process detection, native profile binding, and repeated limiter/ownership reads passed on this host with RTSS running. The test also used the actual elevated 1.2.3 packaged executable and its ASAR entry, reusing one worker without errors. No RTSS profile writes were made, and the temporary RTSS instance was closed afterward. The reported missing Arc Sleep provider and in-game overlay were not reproduced; these read tests do not establish in-game hooking, FPS samples, or visible OSD behavior on the affected system.

These changes address reproduced process churn. The original reporter's flashing-cursor symptom still requires confirmation on their system. The additional screenshot saying that changing old IGS settings helped does not identify a particular driver setting or establish a driver-settings conflict.

## Graphics Apply and sharpening feedback

The general Graphics Apply button previously observed only driver-setting drafts. Screen sharpening uses its own settings service and draft, so changing it could leave the general Apply button hidden. The general action now also observes sharpening changes and saves each kind of setting through its own existing API. The per-card actions remain available.

Global and per-game sharpening cards provide pending/saved feedback and toast messages. Saving a setting is distinct from the runtime actively rendering a recognized foreground game; runtime status and errors remain visible. Percentage controls remain integer sliders from 0 to 100.

## Native sharpening follow-up

Output selection uses Intel vendor identity and the attached foreground monitor rather than a marketing-name substring. Initialization failures retain their stage and HRESULT and back off between retries. The capture loop skips pointer-only updates, retains the duplication frame through render submission, and uses a one-frame queue limit with nonblocking presentation. Frames that cannot be submitted immediately are dropped.

The helper was rebuilt from the source in this change and its production hash pin was updated. A native B580 probe selected Intel device `0xe20b`, opened Desktop Duplication on `\\.\DISPLAY1`, created the overlay resources, and completed 60 render/present calls without a DXGI error. The diagnostic overlay remained hidden; this is an API/resource test, not a visual game test or a latency benchmark. It does not establish image quality, input latency, or game frametimes on driver 9030.

Microsoft documents [nonblocking presentation](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-present) and recommends minimizing the time between [ReleaseFrame and the next acquisition](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-releaseframe). The render loop follows those constraints without introducing a GPU completion wait.
