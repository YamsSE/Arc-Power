## Architecture decisions for this milestone
- **Main process stays plain ESM JavaScript + JSDoc** (M1 style). **Renderer is TypeScript** (plan §5/§8) with a trivial build: add devDeps `typescript` + `esbuild`; `npm run build:renderer` = esbuild bundle `src/renderer/app.ts` → `src/renderer/out/app.js`; `npm run typecheck` = `tsc --noEmit`. index.html links `./out/app.js` + stylesheets (plain .css, no bundling needed). No UI framework, no CSS framework, no runtime deps added — vanilla TS + small component helpers.
- **IPC seam (design it cleanly — this is the security surface):**
  - `src/preload.cjs` (CommonJS — sandboxed preloads cannot be ESM): `contextBridge.exposeInMainWorld('arcPower', {...})` with typed invoke wrappers + telemetry event subscription.
  - `src/main/ipc.js`: registers `ipcMain.handle` for a **whitelist** of channels: health, list-devices, get-capabilities, get-current-settings, apply-settings, reset-to-defaults, waiver-get, waiver-accept, telemetry-start, telemetry-stop. Every handler validates its payload (deviceId is a non-negative integer; apply-settings payload is an object whose keys ⊆ CONTROLS, values are finite numbers or well-formed arrays/objects — reject anything else). apply-settings re-clamps values against the device's capability ranges in main before calling the backend. Telemetry: main owns the TelemetryService per device (start/stop), forwards samples via `webContents.send('telemetry:sample', sample)`.
  - Renderer wrapper `src/renderer/ipc.ts` typed over `window.arcPower` (declare the global in a .d.ts).
- **Pages & routing:** sidebar nav (Dashboard, Overclocking, Fan, Monitoring, Profiles, Tweaks). Monitoring/Profiles/Tweaks = placeholder pages that say "arrives in M2b/M3" (they are NOT in this milestone). Single GPU header across all pages: device name, driver version, health status dot (ok/degraded/error from `health()`), mock-mode badge.
- **Dashboard:** device card (name, driver, caps summary), health status, and a small live readout fed by telemetry (current GPU clock, temp, powerW, fan RPM) — TelemetryService already computes powerW. Graphs are M2b — do not build them.
- **Overclocking page:** one card per supported control, driven by `Capabilities.ranges` (never hardcode limits): labeled slider (min/max/step from ranges, snapped on move), live slider readout with units, "driver current value" readout (may be off-grid), preset chips computed within range (stock/medium/max), per-card Reset-to-default, and a page-level Apply button. Apply → `applySettings` → show per-control result: success toast or error toast mapped from `errorCode` (waiver-not-set / out-of-range / locked-mode / reset-required / unsupported / io-failed each get a clear user-facing message). After apply, refresh state. Unsupported expert controls (gpuLock, vfCurve, VRAM) live in an "Advanced" disclosure, disabled with an "unsupported on this GPU" note on the A770.
- **Waiver dialog:** modal, shown before the first apply when not accepted; text mirrors Intel's warranty warning (overclocking can damage/void warranty, proceed at your own risk); buttons: Cancel / Accept. Only on Accept does the apply proceed.
- **Fan page:** read-only on the A770 (canControl=false): current mode, current 10-point curve rendered in the SVG editor view (no drag), current RPM marker. When canControl=true (mock), full editor: mode toggle (Auto/Curve/Fixed), draggable SVG curve points, add/remove point, point count clamped to `fan.maxCurvePoints`, ascending-temp enforcement, presets, Apply. Keep the editor logic (clamping, sort, point math) in pure functions testable without DOM.
- **Tests:** renderer pure logic (slider snap, presets, curve editor math, error-message mapping, settings payload validation, waiver state machine) with `vitest` (plan §10) or Node 24 native TS type-stripping — your choice, but tests must run under a single `npm test` command together with the existing `node --test` main-process tests (check how: e.g. `npm test` = `node --test && vitest run`, or keep everything node:test-compatible). Existing 112 tests must stay green. Add a test that the product-path IPC/UI flow never auto-accepts the waiver (constructs backend without allowAutoWaiver and asserts no waiver call).
- **Keep working:** `--headless` smoke (real A770, no-op only, exit 0/1) and `--headless --mock` must still work. `npm start` must now open the real UI. Mock mode must make the whole UI usable without hardware.

## Safety rules (hard)
- UI and main-process apply paths both clamp to capability ranges. Never let a renderer payload reach the backend unvalidated/unclamped.
- Waiver: never auto-accept in product code paths. The only auto-accept is the M2a validation script (developer machine, and it must print that it accepted the waiver).
- The real-device validation script MUST restore the prior power-limit value afterwards (and any other value it touched) and verify by read-back. Never leave the device in a changed state.
- No driver/IGS file changes. No git commits. Do not touch tools/probe or docs/igcl-integration.md.
